# Tambola Adda web — agent instructions

These instructions apply to this repository and its worktrees. They adapt the
user-confirmed AlphaGate workflow to Tambola Adda. Current explicit user
instructions take precedence. AlphaGate ticket IDs, historical checkpoints,
datasets, CI cadence and memory paths do not apply here.

## Roles and ownership

- Codex supervises: inspect actual code, review evidence, propose scoped plans,
  and write self-contained, paste-ready Claude prompts. Claude implements.
- Codex must not take over implementation or Git mutations unless the user
  explicitly asks Codex to perform those actions. Read-only review and relevant,
  non-mutating diagnostics are allowed. An authorized asset copy or instruction
  edit does not authorize the rest of the implementation.
- The user handles pushes and merges. Neither agent pushes, opens a PR, merges,
  or publishes by default. Supply commands or PR text at the appropriate phase.
- Use one agent only unless the user explicitly approves delegation for the
  current task. This covers investigation, implementation, testing and review.
- Every paste-ready Claude task prompt must include this exact instruction:
  "Use one agent only. Do not launch subagents, Explore agents, agent teams, parallel agent work or nested delegation unless I explicitly approve it."

## Attribution

- Never add AI/tool attribution or author credits to website copy, code
  comments, filenames, branch names, commit messages, trailers or PR text. No
  "generated by", "assisted by", co-author trailers or equivalent signatures.
- Preserve existing legitimate publisher/contact disclosures and the configured
  Git identity.

## Start and resume checks

At the start of each task, and after a resume or conversation compaction:

1. Reread this file and the latest relevant handoff or agent memory, if present.
2. Verify the actual checkout, branch, HEAD and working-tree status. Preserve
   uncommitted, untracked and ignored work; do not assume it belongs to this task.
3. Identify approved scope, current phase, independently verified evidence,
   Claude-reported results, unresolved decisions and the exact next step.
4. Keep durable rules here and changing task state in the existing handoff or
   agent memory, or the current chat if neither exists. After each authorized
   phase, record a concise checkpoint. Do not rewrite a handoff concurrently
   maintained by another agent; coordinate ownership.

Historical handoffs do not override these workflow rules or later user decisions.
Do not restart completed phases solely because a chat resumed.

## Required workflow

First propose a scoped plan and obtain approval BEFORE Phase 0. Include the
proposed branch, acceptance criteria, in/out-of-scope work, affected files,
validation approach and genuine judgment calls with one recommendation each.
Keep uncertain decisions provisional until investigation resolves them.

- **Phase 0 — Branch:** Create the approved feature branch in the primary
  checkout. Use a neutral, descriptive name with no tool or agent prefix
  (for example `tambola-landing-page`). Do not create a worktree unless the
  user requests one or approves its need. Check that switching preserves all
  existing work and does not disturb a running preview.
- **Phase 1 — Investigate:** Inspect the relevant source, assets, paths and
  deployment assumptions. Report findings, recommended decisions and any scope
  changes. **PAUSE for user approval before building.**
- **Phase 2 — Build:** Implement only the approved scope. Report what changed
  and make the diff reviewable. **PAUSE before Phase 3.**
- **Phase 3 — Validate:** Run affected checks and, for visual changes, inspect
  the actual local site in a browser. Report results, limitations and unresolved
  issues. Codex independently reviews relevant evidence. **PAUSE before Phase 4.**
- **Phase 4 — Ticket status:** When an existing Ticketly ticket is in use, mark
  it Done through the engine workflow and validate/render its existing exports.
  Done means implementation and approved validation complete, not committed,
  merged or deployed. If no ticket/backlog exists, explicitly record this step
  as not applicable; do not invent an ID, create a backlog or add a tracking
  system merely to satisfy this phase.
- **Phase 5 — Local commit:** Only after explicit user approval, stage reviewed
  paths by name, create a LOCAL commit, verify its content and **STOP**. Never use
  blanket staging, automatic checkpoint commits or amend without authorization.
  The commit subject is `<TICKET-ID> — <description>` when a real ticket exists;
  otherwise use the user-approved short subject. No body, trailers or attribution.
- **Phase 6 — User push:** Give the exact push command for the verified branch.
  The USER pushes. Wait for confirmation; neither Codex nor Claude pushes.
- **Phase 7 — PR text:** Only after push confirmation, CODEX supplies the PR text
  in the format below. The user opens the PR and merges it. Do not automatically
  open a PR or treat a request for PR text as permission to do so.
- **Phase 8 — Authorized closeout:** After merge confirmation and authorization,
  verify the merged PR, approved head and actual merge result. Fetch without
  pruning, safely fast-forward main and verify the resulting source. Clean up
  only the authorized clean, merged local branch/worktree without force. Preserve
  unrelated work and ignored files; do not delete remote branches by default.
  Verify GitHub Pages deployment separately before claiming the site is live.
  Update the current checkpoint. Do not defer Phase 4 until this phase.

Approval of one phase does not authorize later phases. Do not combine build,
validation, commit, push and PR steps into one prompt. Do not add micro-phases or
seek separate approval for routine corrections within the current approved phase.
Pause for genuine scope, product, dependency, deployment or destructive decisions.
After a checkpoint, give the next scoped Claude prompt directly rather than
asking whether the user wants the prompt; keep the next phase approval-gated.

## Copy-and-paste Claude prompts

- Put each complete task prompt in one fenced `text` block so the user can copy
  it directly. Do not spread required instructions across surrounding prose.
- Include: exact checkout path; instruction to read this `AGENTS.md`; current
  phase; verified branch/HEAD and relevant dirty state; approved objective and
  acceptance criteria; allowed actions and files; protected state; appropriate
  validation; required report; and the precise stopping point.
- Include the exact single-agent instruction above and the relevant artifact
  preservation rules below. Never rely on Claude seeing this chat or unstated
  approvals. Do not recycle stale hashes, test counts or status claims.
- If a prompt is supplied ahead of approval, explicitly say not to execute it
  until the user approves that phase. Do not include a push or PR-opening action.

## PR text contract

The entire PR-text response must be ONE fenced `text` block, with nothing outside.

- First line: `<TICKET-ID> — <exact backlog title>` when a real ticket exists.
  Copy the title from the actual backlog. Without a ticket, use the approved
  feature title without inventing an ID. Follow the title with a blank line.
- Exactly these headings, in order: `## What`, `## How`, `## Tests`.
- What: 1–3 lines describing the problem and resulting behavior.
- How: 3–5 single-level, one-line bullets explaining the final implementation.
- Tests: accurate check outcomes, counts, selections, failures, skips and
  limitations when applicable. Do not invent suites, gates, mutation checks or
  counts. Do not sum overlapping runs or hide an initial failure.
- Maximum 25 lines including title, blanks and headings, excluding fences.
- No attribution, footer, extra sections or conversational history.
- Mechanically verify the title, headings, bullet count and line count before
  sending. Describe the final change for a reviewer who has not seen this chat.

## Ticketly

When the user asks to plan a backlog, break work into tickets, or use Ticketly:

1. Run `ticketly home` to locate the engine.
2. Read the engine's `codex/AGENTS.md` and follow its instructions.

Reuse an existing backlog and tickets. Do not guess ticket IDs, invent scope,
hand-edit generated exports, or introduce Ticketly solely because phases exist.

## Validation and evidence

- Distinguish implementation/validation complete, Ticketly Done, committed,
  pushed, merged and deployed. One does not prove the next.
- Clearly separate Claude's reported results from Codex's independent checks.
- Use proportionate validation. Prefer affected checks and realistic browser
  journeys. Do not add tests that mirror implementation or repeat broad suites
  without a concrete reason. After a fix, rerun affected checks; broaden only
  for unresolved interactions or an agreed gate.
- For homepage changes, check mobile/desktop layouts, keyboard navigation,
  visible focus, contrast, reduced motion where relevant, image loading and
  layout stability, internal links, metadata and preserved privacy/support pages.
- Inspect actual tooling before naming commands or gates. Do not introduce a
  framework, package manager, build pipeline, CI workflow, analytics or external
  integration without scope approval. Preserve existing GitHub Pages deployment
  behavior; do not enable or dispatch new hosted jobs without authorization.
- Before calling something a blocker, give concrete evidence, name the action it
  blocks and offer a practical alternative. Label uncertainty and inference.
- Verify current official sources for provider rules, crawler behavior and SEO
  claims. Do not promise indexing, rankings, AI citations or App Store approval.

## Product, routes and previews

- Preserve the existing `/privacy/` and `/support/` URLs under the GitHub Pages
  project base, their existing content and anchors unless changes are approved.
  Keep page links and assets compatible with project-relative hosting.
- Preserve established branding and use real user-supplied app screenshots.
  Do not fabricate app UI, testimonials, ratings, prices or product capabilities.
- Confirm the latest user-provided App Store status before writing availability
  copy. Submission does not establish approval or release. Do not add a working
  download badge, release date or platform-availability claim without evidence.
- Keep important product information readable in HTML. Use search phrases
  naturally; structured data must match visible, verified facts. Do not treat
  AI-specific files as a guarantee of discovery or conflate search with training.
- Before a preview or walkthrough, explain its purpose, source checkout/commit,
  URL, data used, setup changes, what the user should test and how it will stop.
  Distinguish the running page from Git source and the deployed site. Stop owned
  preview processes afterward unless the user asks to retain them. Report
  shutdown separately from deletion; do not restart an intentionally stopped
  preview or delete retained data without authorization.

## Files and artifacts

- Reuse this repository's structure. Product screenshots belong in
  `assets/screenshots/`; preserve the supplied originals and resolution folders.
  Necessary web-optimized derivatives may live alongside the site's assets when
  within approved implementation scope. Do not replace originals silently.
- Do not automatically create per-ticket folders, evidence archives, investigation
  directories, walkthrough copies, retained build copies or sibling Desktop
  folders. Keep concise results in the current handoff, agent memory or chat.
- Retain extra screenshots, logs, ZIPs or bundles only when requested or required
  for the approved deliverable. Explain their purpose and use an appropriate
  existing location. Routine temporary files may use tool-managed scratch space.
- Inspect ignore coverage before generating large or sensitive files. Never
  force-add local artifacts or secrets. Source, intended documentation and product
  assets belong in their normal tracked locations.
- Preserve all unrelated work and original assets. No reset, force operations,
  destructive cleanup, source-folder deletion or remote-branch deletion without
  explicit authority. Do not assume verification of a copy authorizes deletion.

Keep communication concise, confined to the current task and clear about the
remaining work. Do not silently expand scope or import AlphaGate-only machinery.
